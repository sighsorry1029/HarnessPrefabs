# Valheim 1.0 compatibility checks

These checks use the final ILRepack output and unmodified game DLLs. They do not launch Unity or establish a network connection. Run from the repository root with .NET SDK 9 and the mod's .NET Framework 4.8 targeting pack available. Both test runners use .NET 9: .NET Framework cannot resolve Unity 6's netstandard 2.1 Span overloads during reflection. The mod itself still targets .NET Framework 4.8 and runs inside the game's Unity/Mono runtime.

```powershell
$originalManaged = 'C:\path\to\original\valheim_Data\Managed'
$bepinexCore = 'C:\Program Files (x86)\Steam\steamapps\common\Valheim\BepInEx\core'
dotnet build HarnessPrefabs.csproj -c Debug -p:DeployToGame=true
dotnet build tests/HarnessPrefabs.CompatibilityTests.csproj -c Debug "-p:OriginalManagedPath=$originalManaged"
dotnet ./tests/bin/Debug/net9.0/HarnessPrefabs.CompatibilityTests.dll ./bin/Debug/HarnessPrefabs.dll $originalManaged $bepinexCore
dotnet build tests/MetadataChecks/MetadataChecks.csproj -c Debug
dotnet ./tests/MetadataChecks/bin/Debug/net9.0/MetadataChecks.dll ./bin/Debug/HarnessPrefabs.dll $originalManaged $bepinexCore ./tests/bin/metadata-client.json
```

Repeat the two executables with the matching dedicated server's original `valheim_server_Data/Managed` directory. `OriginalManagedPath` changes test compilation references; `CorlibPath` changes mod compilation references. Neither applies a publicizer. Debug deployment copies only the final merged mod DLL to the local game's plugins directory.

- CompatibilityTests: twenty cases for the native item payload reader, durability quantization, item identity/state comparison, malformed payload rejection, absence of a Jotunn assembly reference, icon alpha validation, ArmorStand cloth reference filtering, and hand equipment state. The item fixture uses the native game `ItemData.Load`; it is not a complete ArmorStand transaction or a `SaveToZDO` integration test. The icon fixtures invoke the final DLL's pixel validator; they do not render textures or verify GPU shader behavior. Cloth fixtures use uninitialized objects of the original MagicaCloth/Unity collider types in an `ArrayList` to model incompatible serialized references without corrupting a typed CLR array or calling Unity. They check valid/null entries, order/duplicates, source preservation, all-invalid lists, and repeated filtering; they do not exercise Unity deserialization or cloth simulation.
- MetadataChecks: direct game method/field accessibility, declared Harmony target existence/uniqueness and injected argument types, explicit generic FieldRef targets, no stale `ZRoutedRpc.Everybody` field load. Resolves type forwarders when comparing client/server types. It does not execute patches or exhaustively verify dynamic reflection and third-party code.
- The pinned ServerSync source/verification location is recorded in `Libs/ServerSync.md`. Its isolated BufferHarness can take the final merged mod DLL as its candidate. It checks packet buffering with a fake transport, not actual Steam/PlayFab login.

Standalone CLR tests cannot execute Unity native calls or establish behavior in the game's Unity/Mono runtime. Actual UI, soft asset lifecycle, Harmony application and multiplayer tests therefore remain separate; see `VALHEIM-1.0.7.md`.

The hand fixtures invoke the final DLL's `TryEquipHandState` on uninitialized managed Player/Inventory objects. Test-only HarmonyX 2.16.0 supports the .NET 9 runner; the mod's game Harmony dependency is unchanged. In the test process only, `Humanoid.EquipItem` is replaced with a controlled action and `ZSyncAnimation.GetHash` with a constant because character static initializers otherwise call Unity's native Animator. The original game DLL files are unchanged. The fixtures check normal equip order, synchronous shield auto-equip without a second equip call, real equip refusal, a different shield, an invalid equipped flag, missing inventory membership, and unexpected hidden equipment. They do not load SecondaryAttacks or verify the full transaction, rollback, native visuals, or game Harmony runtime. Before the hand fix, the auto-equip fixture fails; the other nineteen cases pass.

ArmorStand hand equipment regression (requires actual game execution):

- On each of `ArmorStand`, `ArmorStand_Male`, and `ArmorStand_Female`, put on and retrieve sword + shield and axe + shield sets with Alt+E. Include the reported EpicLoot DeepNorth set. Repeat with SecondaryAttacks `Auto Equip Last Shield` on and off, and with the remembered shield being the incoming shield or a different inventory shield. Confirm the intended item instances are equipped and no left-hand rollback error occurs.
- Check weapon-only, shield-only, two-handed, and sheathed sets. On a genuine equip refusal, verify rollback restores both sides with no lost or duplicated items. Verify EpicLoot/custom data, durability, quality, variant, and cheat state remain intact after swap, save, and reconnect. Repeat client/host/dedicated multiplayer checks; isolated tests do not establish those results.

ArmorStand cloth regression (requires actual Unity execution):

- Valheim 1.0.17's original `ArmorStand_Male` and `ArmorStand_Female` assets contain five Unity `CapsuleCollider` references in `VisEquipment.m_clothColliders`, which now expects `MagicaCloth2.ColliderComponent`. The prefix on private `VisEquipment.SetupCloth(GameObject)` replaces only incompatible lists on those two stands. Valid Magica references and null entries remain; collider components are not destroyed. The guard is independent of the swap toggle, Piece creator, and YAML access because normal attachment, saved stands, and remote visuals use the same cloth path. No extra per-frame cache or cleanup is introduced.
- Equip `CapeDeepNorth` and `CapeDeepNorthMage`, separately as normal and EpicLoot items. Attach normally and via Alt+E to each of `ArmorStand`, `ArmorStand_Male`, and `ArmorStand_Female`. Check the male/female correction warning occurs only when incompatible references are found; repeated equipment changes must not recreate the warning for an already corrected list. Confirm player cloth and the base stand are unchanged and no native crash occurs.
- Check legitimate Magica collider references supplied by another mod are preserved. Male/female stands with all five invalid entries removed may show cape/body clipping; this patch does not synthesize replacement physics colliders.
- Repeat with swap disabled, a stand loaded with a saved cape, world exit/re-entry, and a remote observer/client on a dedicated server. Compare item identity, quantity, durability, quality, variant, and EpicLoot custom data before/after swapping and saving. The rendering client needs the patch; changing only a dedicated-server DLL cannot protect an unpatched client's cloth code.

Piece injection regression (requires actual Unity execution):

- For a managed prefab that originally lacks `Piece`/`StaticTarget`, compare natural and player-built instances. The injected Piece must report false from `IsRandomTarget`/`IsPriorityTarget` when creator is zero and retain its target flags for a player creator. Exercise an AI static-target search as well; ownership alone must not count as player construction. Confirm existing native Piece target settings are unchanged, including after YAML refresh and world re-entry.
- Try a prefab without a root `ZNetView`, including one with a view only on a child, as both Public and Admin. Expect a named warning, no new Piece, no Hammer entry/selection, and no placement-offset/ghost-collider registration. Reference discovery may still list it. A valid root-view prefab must still register when the debug tab is hidden and appear when it is enabled.
- With a client/host and a dedicated server, build a valid chest, Pickable and WearNTear piece, inspect it remotely, save/reconnect, then remove it. Check stored contents and creator survive, inventory is not cleared on reload, and natural drops are preserved. Compare hammer removal and attack destruction separately: adding Piece does not turn a Destructible into WearNTear or guarantee equal refunds. Check natural collider/layer/rotation behavior separately; existing prefab fixups remain unchanged.

Hammer tab appearance regression (requires actual Unity execution): enable debugmode while Categories is selected, and again while another tab is selected. The newly attached HarnessPrefabs tab must be clickable and unhighlighted. Select it using mouse and keyboard/gamepad navigation, then switch away: only the active tab should be highlighted. Repeat after toggling `Show Harness Tabs`, reopening the menu, and re-entering the world. Attaching the tab must preserve the current tab and must not invoke another tab's selection callback.

For the icon renderer fix, restart the game and compare Wood box (`CastleKit_braided_box01`), Black Marble Post (01) (`blackmarble_post01`), and Standing Iron Torch (Eternal) (`CastleKit_groundtorch`). Their regenerated PNGs use `BepInEx/cache/HarnessPrefabs/valheim-<game version>-icons-r2`; old `valheim-1.0.7-r1` files are preserved and ignored. Check first generation, cached reload, framing and transparency, authored icons, world re-entry, and absence of repeated render attempts or gameplay/network effects from the visual clones. A fully transparent render should retain the fallback icon and log the prefab name, without storing a new blank PNG.

Also check `TreasureChest_dvergrtower`, `TreasureChest_dvergrtown`, `blackmarble_head_big01`, and `blackmarble_slope_1x2`: each pair shares an original Piece sprite, which must not prevent snapshots of their actual models. Existing successful snapshot caches remain valid. On render failure the original icon should remain; native buildables excluded by HarnessPrefabs must keep their own icons. World exit must restore the original sprites before generated textures are released.

Hammer selection regression (requires actual Unity execution): select a normal wall, then click two different pieces from each HarnessPrefabs group and verify both the placement ghost and the built prefab match the clicked icon. Repeat after closing/reopening the menu, switching tags/tools, refreshing YAML, and leaving/re-entering the world. Native `Player.SetSelectedPiece(Piece)` looks up `PieceTable.m_availablePiecesByCategory`; the `UpdateAvailable` postfix adds admin pieces to this selection index only. Check Categories, Materials, Recent, and Favorites remain free of these pieces, including after favoriting/building them. Disable debugmode or `Show Harness Tabs`, revoke admin status, and change an active prefab rule to hidden: the tab/selection must be removed and the old admin ghost must not remain usable. Test ordinary clients and a dedicated server as well. The metadata checker validates the postfix target and private field injection; the isolated CLR tests cannot create Unity objects, click the menu, or prove placement behavior.
